# 3.8 显存 profiling 完整教程

配套脚本：`mem_profile.py`（放到 `scripts/` 下，与 `benchmark.py` 同目录）。

> **验证状态**：脚本的纯 Python 部分（参数个数、理论估算、快照事件流解析、激活拟合、汇总表）已用合成数据测过。涉及 GPU 的部分（`memory_allocated`、快照记录与导出、子进程调度）**没有在 GPU 上跑过**。快照的字段在不同 torch 版本里有差异，所以第一次请先用小配置试通（第 3 节），再放大。

---

## 1. 先搞清楚3.8这一节要回答什么

| 表里的格子 | 本质问题 |
|---|---|
| forward 峰值 | 只做推理（no_grad，没有优化器）需要多少显存 |
| 完整训练步峰值 | 训练一步（含 Adam）最高占用多少 |
| 理论静态显存 | 权重、梯度、Adam 状态这三块"不随 ctx 变"的部分 |
| 主要占用来源 | 峰值时刻显存被什么占着 |

附加问题：

| 问题 | 本质 |
|---|---|
| 激活值显存与 ctx 的关系 | 线性项（随 N=B·T）与 T² 项（attention 分数）各占多少 |
| 2.7B 理论峰值 | 用校准过的公式外推 |
| 最大的单次分配 | 哪个张量最值得优化 |
| 混合精度对峰值的影响 | bf16 是否真的省显存 |

**与 3.5 的区别**：3.5 只要一个峰值标量；3.8 要知道峰值出在训练步的哪个阶段、被什么占着，所以需要按阶段读峰值、做显存快照。

## 2. 先写理论（先写后测）

静态部分（与 ctx 无关）：

| 项 | 公式 |
|---|---|
| 权重 | 4P |
| 梯度 | 4P |
| Adam 状态 | 8P |
| **完整训练步静态** | **16P** |
| 仅推理（fp32 权重） | 4P |

激活部分沿用 11.6：`L·4·(5·N·d_ff + c·B·h·T² + other·N·d) + 16·N·V` 字节，取 c=2、other=20（这两个常数是估计值，small 上这个公式给 6.16 GiB，实测 5.04 GiB，约高估 20%）。

按本配置（SwiGLU 三个矩阵、词表 10000、batch 4）算出来：

| 模型 | ctx | P | 4P (GiB) | 16P (GiB) | 激活估算 (GiB) | 峰值估算 (GiB) | 一个 B·h·T² fp32 张量 | logits（N×V fp32） |
|---|---|---|---|---|---|---|---|---|
| medium | 128 | 423.2M | 1.58 | 6.31 | 2.14 | 8.44 | 4 MiB | 19.5 MiB |
| medium | 512 | 423.2M | 1.58 | 6.31 | 10.81 | **17.11** | 64 MiB | 78.1 MiB |
| large | 256 | 969.4M | 3.61 | 14.45 | 8.59 | **23.04** | 20 MiB | 39.1 MiB |
| 2.7B 配置 | 128 | 3.407B | 12.69 | 50.77 | 6.8 | 57.6 | — | — |

**预测 OOM 点**：显卡按 16 GiB 算（脚本会打印实际总显存）。

- medium ctx 512 fp32：估算 17.1 GiB 超过 16 GiB，但公式约高估 20%，所以**处在边界上**，要实测。
- large ctx 256：静态 16P 就是 14.45 GiB，估算 23 GiB，**预计 OOM**。把它记为预期结果，不是 bug。
- 2.7B 这个配置的 P 是 3.4B，不是名字里的 2.7B（名字里的 2.7B 对应两矩阵 FFN 和更大的词表）。以脚本打印的 P 为准。

bf16 autocast 的静态部分：权重、梯度、Adam 仍然是 fp32（16P），另外 forward 期间会缓存一份 bf16 权重副本（约 2P，是否保留要以实测为准）。所以**不要预期 bf16 把静态显存减半**。

## 3. 运行

### 3.1 准备

```bash
cd /data2/c220/hz/cs336
cp /path/to/mem_profile.py scripts/        # 与 benchmark.py 同目录
nvidia-smi                                  # 确认卡空闲；多卡时用 CUDA_VISIBLE_DEVICES 隔离
```

脚本依赖 `cs336_basics.model.BasicsTransformerLM`、`cs336_basics.optimizer.AdamW`、`cs336_basics.nn_utils.cross_entropy`，与你的 benchmark.py 一致。

### 3.2 第一步：小配置试通（1 分钟）

```bash
CUDA_VISIBLE_DEVICES=0 uv run python scripts/mem_profile.py --model small --ctx 128 256 --dtype float32
```

检查这几件事，任何一条不满足都先别往下做：

| 检查 | 期望 |
|---|---|
| 每个配置打印一行"理论" | P = 128.6M，16P = 1.92 GiB |
| 最后一行 `A ... B ... C ... status=OK` | 三个数都有值 |
| `results/mem/` 下有 `mem_*.pickle` 和 `res_*.json` | 存在，pickle 不是空文件 |
| 汇总里"快照解析"不是"无快照解析" | 有"归类"和"最大分配" |
| "事件流峰值"与"allocator 口径"接近 | 差别在百分之几以内 |

如果"快照解析"里出现 `trace_error`，说明你的 torch 版本里快照事件的字段与脚本假设不同。其余结果不受影响（表里的数值都来自 allocator 统计）。这时把 `trace_error` 的内容发给我，我来改解析。

### 3.3 第二步：正式运行

```bash
# medium：两个 ctx × 两个 dtype
CUDA_VISIBLE_DEVICES=0 uv run python scripts/mem_profile.py --model medium --ctx 128 512 --dtype float32 bfloat16

# large：预计完整训练步 OOM，要的是 OOM 时的快照和 forward 阶段的数据
CUDA_VISIBLE_DEVICES=0 uv run python scripts/mem_profile.py --model large --ctx 256 --dtype float32 bfloat16
```

每个配置在独立子进程里跑，所以 cuBLAS workspace、allocator、Adam 状态不会互相污染。OOM 会被记录下来，不会中断后面的配置。

### 3.4 脚本在做什么（对应输出里的 A、B、C）

| 阶段 | 做法 | 为什么 |
|---|---|---|
| **A** | 刚初始化、**还没有优化器**，no_grad 前向，预热后 reset 峰值再测 | 得到纯推理峰值。必须在创建优化器之前，否则 Adam 状态会混进来 |
| **B** | 带图前向，读前向前后 `memory_allocated` 的差 | 得到"保存给反向的激活"。随后 backward 并清梯度 |
| **C 预热** | 创建 AdamW，跑 3 个完整步 | 让 Adam 状态、cuBLAS workspace、allocator 进入稳态 |
| **C 记录** | **只对一步**开启快照记录；forward、backward、optimizer 每段前 `reset_peak_memory_stats`，段后读峰值 | 得到每个阶段自己的峰值，所以知道峰值出在哪个阶段 |
| **D** | 解析快照事件流，重建峰值时刻存活的块 | 得到峰值构成和最大分配 |

## 4. 怎么读输出

### 4.1 主表

```
| 模型 | ctx | dtype | forward 峰值(no_grad) | 带图 forward 峰值 | 完整训练步峰值 | 峰值阶段 | 理论 4P | 理论 16P | 峰值估算(11.6) | 估算÷实测 | 状态 |
```

| 列 | 含义 |
|---|---|
| forward 峰值（no_grad） | 探针 A。**对应作业表的"forward 峰值"** |
| 带图 forward 峰值 | 探针 B，训练时的前向（含 Adam 状态不在内，因为 B 在创建优化器之前） |
| 完整训练步峰值 | 探针 C 三个阶段峰值的最大值。**对应作业表的"完整训练步峰值"** |
| 峰值阶段 | 三个阶段里峰值最高的那个 |
| 估算÷实测 | 11.6 公式的偏差；预期略大于 1（高估） |

**怎么理解"峰值阶段"**：典型情况是峰值在 **backward**：激活还没有释放完，梯度已经在累积。这是需要验证的假设，不是结论，以你的数据为准。

### 4.2 构成表

```
fwd结束: 权重 | Adam | 激活/其他 | 合计     bwd结束: 权重 | 梯度 | Adam | 其他 | 合计
```

- forward 结束时的"激活/其他"就是保存给反向用的激活（autocast 下还包含缓存的 bf16 权重副本）。
- backward 结束时激活已释放，"其他"应该很小；它不小说明有张量没释放（比如还有引用着的 loss 或 logits）。
- 两处的权重、Adam 应该一致，并且等于理论的 4P 与 8P。**对不上先查：是否真的创建了优化器、权重是不是 fp32。**

### 4.3 快照解析

```
归类：静态(权重+Adam) x；backward(梯度/临时) y；forward(激活) z；...
最大分配  67.1 MiB  model.py:xx attention
```

- 归类是**启发式**（按调用栈的文件和函数名分类）。反向分配发生在 autograd 引擎线程，调用栈常常没有 Python 帧，所以会落在"backward"或"other"，这本身就是特征。
- "事件流峰值"与"allocator 口径"应当接近。差得多说明 `--max-entries` 太小（环形缓冲覆盖了早期事件），调大再测。
- 最大单次分配的栈是 Python 文件名加行号，对着你的 `model.py` 就能找到是哪一行。

## 5. 用 memory_viz 看时间线（可选但建议）

1. 打开 https://pytorch.org/memory_viz ，把 `results/mem/mem_medium_ctx512_float32.pickle` 拖进去（在浏览器里本地解析，不上传）。
2. 选 **Active Memory Timeline**。
3. 读法：

| 看什么 | 怎么看 |
|---|---|
| 整个训练步的曲线 | 前向阶段持续上升（激活积累），反向阶段先继续上升后下降，optimizer 阶段有一段临时张量 |
| 最高点在哪个阶段 | 与表里的"峰值阶段"对照，应当一致 |
| 悬停色块 | 看这块显存是谁分配的，对着调用栈 |
| 大色块 | 找 T² 大小的分数矩阵、N×d_ff 的 FFN 中间量、N×V 的 logits |

4. 要看碎片，选 **Allocator State History**，比较 reserved 与 allocated。

注意：快照只记录开启记录之后的事件，所以权重和 Adam 状态（记录前就存在）不在色块里，它们是时间线的"基底"。

### 6.2 附加问题

**激活值显存与 ctx 的关系**

脚本在"附加问题 1"里打印：

```
ctx 增大 4×：激活增大 x×（纯线性项应为 4×，纯 T² 项为 16×）
拟合 act = a·N + b·B·h·T²：每层线性项等效 ... 份 N×d 张量（11.6 取约 40），T² 项等效 c = ...（11.6 取 2）
```

解读：

- 倍数在 4 附近：线性项主导（FFN 中间量、残差、投影输入）；
- 倍数明显大于 4，往 16 靠：T² 项（attention 分数及其 softmax 中间量）开始显著；
- 拟合值替换 11.6 里的 c 和 other，**这就是校准**。注意拟合只用了 2 个 ctx 点，要加 256 才能检验线性假设。

建议把 medium 多加一个 ctx：`--ctx 128 256 512`。

**2.7B 理论峰值**

脚本在"附加问题 2"里用本配置的 P、你拟合出来的 c 与 other 外推，给出 16P、激活估算和合计。写答案时同时写出：

- P 的值和来源（3.4B，SwiGLU 三矩阵配置）；
- 用的 batch 与 ctx（默认 4 和 128，用 `--theory-batch`、`--theory-ctx` 改）；
- 激活估算的 c、other 是拟合值还是默认值。

**最大的单次分配**

用"快照解析"里每个配置的"最大分配"。我的假设（**未验证**）：ctx ≤ 512 时可能是 logits 或其转换（N×V×4B，ctx 512 约 78 MiB），而不是 attention 分数（medium、ctx 512 约 64 MiB 每个张量）。ctx 越大 T² 增长越快，会反超。以实测为准，写答案时给出张量大小、形状和对应的代码行。

**混合精度对峰值显存的影响**

脚本在"附加问题 4"里打印 bf16 与 fp32 的比值（保存的激活、no_grad 前向峰值、完整步峰值）。

解读：

- 保存的激活：一部分张量以 bf16 保存，应当下降；但残差流可能仍是 fp32，所以不会减半；
- no_grad 前向峰值：权重仍是 fp32，加上 autocast 缓存的 bf16 权重副本，**可能不降甚至上升**；
- 完整步峰值：静态的 16P 不变，所以只有激活部分能省，比值会比激活的比值更接近 1。

### 6.3 "主要占用来源"怎么写

用构成表和快照归类各写一句，例如：

> medium / ctx 512 / fp32：静态 X GiB（权重 a、梯度 b、Adam c）+ 激活 Y GiB。峰值出现在 backward 阶段，最大的单次分配是 ……（形状、代码位置）。

模板里的数字都来自你的运行结果，不要用本教程里的估算值。

## 7. 预期会发生什么（用来检查测量对不对）

| 检查 | 期望 | 不满足说明 |
|---|---|---|
| bwd 结束时的"权重"一列 | = 4P（fp32 权重）| 权重不是 fp32，或模型没按预期构建 |
| bwd 结束时的"Adam"一列 | = 8P | 预热步数不够，Adam 状态没分配全 |
| bwd 结束时的"梯度"一列 | = 4P | 梯度没有清或没有产生 |
| 同一模型不同 ctx 的权重、Adam、梯度 | 完全相同 | 测量混入了别的东西 |
| 峰值阶段 | 常见是 backward | 若是 optimizer，检查 AdamW 是否逐参数分配了大临时张量 |
| 估算÷实测 | 略大于 1 | 远大于 1 说明 c、other 取大了；小于 1 说明漏估了某些张量 |
| 激活随 ctx 增长 | 4 倍到 16 倍之间 | 小于 4 倍说明有常数项（如 logits 相对 T 固定的部分）或测量有误 |

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| `OOM(A…)` 或 `OOM(build)` | 连推理都放不下。检查是否有别的进程占卡 |
| `OOM(C(记录的训练步))` | 预期（如 large）。表里仍有 A、B 的数值；快照是 OOM 时导出的，用 memory_viz 看 OOM 瞬间占了什么 |
| `OOM(C(预热))` | 预热阶段就放不下，没有快照。把它当作"完整训练步放不下"，写 OOM，并按 16P 估算原因 |
| 子进程 `FAIL(rc=…)` | 不是 OOM 的错误，看终端里子进程的报错 |
| `trace_error` | torch 版本的快照字段不同，把错误信息发给我 |
| "事件数达到 max_entries" | 调大 `--max-entries`（如 1000000） |
| 事件流峰值与 allocator 口径差很多 | 同上，或快照记录前有大块被释放 |
| bf16 下 forward 峰值比 fp32 还高 | 可能是缓存的 bf16 权重副本；用 `--dtype bfloat16` 单独看 no_grad 前向的构成 |
| 数字每次运行略有不同 | allocator 的块大小取整与碎片，差在 1% 以内正常 |

## 9. 补充测量（作业 3.8 之外，可选）

| 想验证 | 做法 |
|---|---|
| attention 分数矩阵到底多大 | 在快照里找 `B·h·T²·4` 字节（medium、ctx 512 是 64 MiB）大小的块，对着栈看是 scores、softmax 的哪一步 |
